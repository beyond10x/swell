## Context

Slice 9 brings `Map`, `Set`, `WeakMap`, `WeakSet`, `Proxy` and `Reflect` (`epic:slice-09-collections-proxy-reflect`; `docs/design/engine.md`, section 12, item 9). `Map` and `Set` keep their entries in insertion order, find a key in constant time on average, keep an iterator that is in the middle of the entries working while entries are added, deleted and cleared (`#sec-map.prototype.foreach` and `#sec-createmapiterator`: an entry added before the iterator reaches its position is visited, a deleted one is not), and compare keys by SameValueZero (`#sec-samevaluezero`: `-0` and `+0` are one key, `NaN` is one key, two Strings with the same code units are one key). The engine has the keyed hash map (`crates/swell/src/heap/map.rs`, `KeyedMap`, SipHash keyed by `Seeds::hash_key`, HOST-145) and an ordered list with an index map above `SMALL` entries for properties (`crates/swell/src/object/property.rs`, `KeyedList`, line 188), but no table of entries keyed by a value. This story builds that table, in the engine and with its own unit tests, so that `story:map-and-set` builds the two builtins on it and `story:set-methods` and `story:map-upsert-and-group-by` reuse it. It is in order 1 and depends on no story; it has no case of test262 (every case reads `Map` or `Set`, which this story does not define).

The epic's open question "Where the SipHash and the host-seeded key first exist" is settled on the base (`62c7cf59`): `heap/map.rs` and `Seeds::hash_key` (HOST-145, delivered); this story uses that hasher (`Heap::hasher`) and adds none.

Design it builds on, by name: `docs/design/engine.md` decision 4 ("Objects": an ordered list with an index map above a small size; "Memory budget": every growth charged before it happens; "Collector": the collector allocates nothing) and decision 3 ("The step budget"); `docs/design/host-interface.md` decision 3 (HOST-145: no order the script can observe comes from a hash map) and HOST-25 and HOST-214 (`[slice 9]`, which `story:map-and-set` moves with this table under it). How the table holds a String key is not stated by the design; this story takes the default of question D1 of the decomposition (below, "Change").

## What later stories reuse

`EntryTable` with its cursors: `story:map-and-set` (the [[MapData]] and [[SetData]] of each object and the iterators, and `release_cursors`, which it calls from the collector), `story:set-methods` (the loops of `union` to `isDisjointFrom` over a table and its cursor) and `story:map-upsert-and-group-by` (`getOrInsert`, `getOrInsertComputed` and the groups of `Map.groupBy`). `story:weak-map-and-weak-set` does not use it (its tables are keyed by an object or a symbol without order).

## Domain relations

- A table → its entries: one to many, ordered by insertion, each entry a key and (for a map) a value, a deleted entry a hole until compaction — inferable (inferred from ECMA-262 `#sec-map-objects` and `#sec-set-objects`, where [[MapData]] and [[SetData]] are Lists of records whose deleted elements become `empty`; no ess/1 document declares it: the host model `spec/domains/host.yaml` holds no engine value, and ESS does not restate the slots of ECMA-262, `AGENTS.md`, "Rules").
- A table → its cursors: one to many, each cursor a position in the entries that compaction and `clear` move — inferable (inferred from `#sec-map.prototype.foreach`, note 1, and `#sec-%mapiteratorprototype%.next`; no ess/1 document declares it, for the same reason).

## Change

Failing tests first: the unit tests below are written before the code and fail to compile on the base (the module does not exist).

- `crates/swell/src/object/keyed_entries.rs` (new; its `mod` line in `crates/swell/src/object/mod.rs`): `EntryTable`, the List of [[MapData]] and [[SetData]]: a `Vec` of entries in insertion order (key, value; a hole after a deletion), and above `SMALL` live entries (`object/property.rs` line 188, the same bound and the same reason) a `KeyedMap` (`heap/map.rs`) from the canonical key to the position, made with `Heap::hasher` and charged by `KeyedMap::table_bytes_for` before it is made. The canonical key (`#sec-samevaluezero`, with `CanonicalizeKeyedCollectionKey`, `#sec-canonicalizekeyedcollectionkey`: `-0` becomes `+0`) is one word: an object, a symbol, a boolean, `undefined`, `null` by its handle or tag; a Number by its bits with every NaN one NaN and `-0` as `+0`; a String by the handle of its atom (decision D1, default A: a String key is interned once at insertion with `Heap::intern_string` (`crates/swell/src/heap/string.rs` line 315), so a lookup is one hash of one word and two equal Strings are one atom; an atom is held weakly by the atom table, and the table's `trace` lists the atom of each live key, so it stays while its entry does). `get`, `has` and `delete` look the atom up with `Heap::atom_of` (`heap/string.rs` line 289), which makes nothing, and a String with no atom is in no table. Not `key_from_string` (`crates/swell/src/ops/conversion.rs` line 363): that turns an array-index String such as `"0"` into `Key::Index`, while a collection keeps `"0"` and `0` apart, so every String, `"0"` included, is a String atom here. Interning and looking up a String key reads its code units: the operation charges a step per code unit past `FREE_CODE_UNITS` (32, `crates/swell/src/ops/testing.rs` line 21) with `charge_code_units` before it reads them, as `key_from_string` does.
- Operations, each `pub(crate)`: `find`, `insert` (appends or overwrites the value in place, the position unchanged), `delete` (makes a hole, the index map entry removed), `clear` (every entry a hole, as `#sec-map.prototype.clear` sets each to `empty`, then the storage dropped), `len` (live entries), `entry_at(position)` and `next_live(position)` for cursors. Compaction when at least half the entries are holes and no cursor would skip a live entry: positions of live entries move down, the index map is rebuilt or updated, and every registered cursor whose position is above a hole moves down by the holes before it (the `compacts` rule of `object/property.rs` line 343 is the model). A cursor is registered with the table (`open_cursor(owner)` answers its id; `owner` is the handle of the iterator object that holds the cursor, kept in the cursor's entry and not traced, or none for a `forEach`), so a cursor's position is always the index of the next entry to visit after any operation; `clear` sets every cursor to the end of the empty storage, so an iterator that runs on after `clear` sees only entries added after it (`#sec-map.prototype.clear` with `#sec-%mapiteratorprototype%.next`).
- Who releases a cursor (Map and Set Iterators have no `return`, so `for (k of m) break;` abandons one): `close_cursor(id)` when an iterator answers done and on every exit of a `forEach`, normal or abrupt (the builtin closes it before it returns its completion, `story:map-and-set`); and for an iterator that is dropped unfinished, the collector: `release_cursors(&mut self, is_live: &dyn Fn(Handle) -> bool) -> u64` (`Handle` of `crate::heap::arena`; a cursor's owner is kept as the `handle` of the iterator's `ObjectRef`) drops every cursor that has an owner for which `is_live` answers false, and keeps every cursor that has no owner: such a cursor belongs to a walk in Rust that holds it while it runs (`forEach`, and the walks of `this` in `story:set-methods`), and only that walk's `close_cursor` releases it. `story:map-and-set` calls it from `heap/collect.rs` after the mark phase and before the sweep, for every marked Map and Set, with the mark bit of the owner as `is_live` (through `Arena::visit_marked_mut` of `heap/arena.rs`, which that story adds), so a cursor never outlives its iterator past the next collection and the owner's handle is not yet reused when it is read. No later story is needed for it. The cursor list grows by doubling and each growth is charged before it with `Agent::charge_bytes`; the table keeps the bytes charged for the list in a count of its own. A credit is only storage given back: the list is freed, and its bytes credited and the count set to 0, when it holds no cursor, so `close_cursor` of the last open cursor frees and credits the list, and `close_cursor` of one cursor of several credits nothing and keeps the list's capacity. `release_cursors` drops cursors in place (`Vec::retain`, which moves no storage) and, when none is left, frees the list (replaced by an empty `Vec`, which allocates nothing) and answers the count it held; when a cursor is left it keeps the capacity and answers 0. It frees and never reallocates, so the collector that calls it allocates nothing. The free of the table credits only what the count still holds, so no byte is credited twice.
- Bounds. Steps: every operation charges its steps before its work through the `Agent` that owns the heap (`Agent::charge_steps`): one for `find`, `insert` and `delete`, at most `SMALL` comparisons below the index map counted as that step (as `KeyedList`), a String key its code units past `FREE_CODE_UNITS`; compaction one step per entry it moves and one per cursor it moves; `clear` one step per 64 entries and one per cursor it resets; `open_cursor` one step; a loop over the table (a cursor) one step per entry visited, charged by the caller. Memory: the entry storage and the index map grow by doubling and each growth is charged before it with `Agent::charge_bytes` (`object/mod.rs` line 515), and credited when it shrinks or the table is freed; a table made at the memory budget's last bytes ends the run with `Terminated(MemoryBudget)` and leaves the table as it was. Collector: `EntryTable::trace` lists every live key and value; it allocates nothing and visits each entry once (a worklist push per value, `heap/collect.rs`). Depth: no operation calls script (SameValueZero runs no code), so no re-entry and no frame is added. Run loop: nothing is added to `Agent::execute`.
- Tests, `#[cfg(test)] mod tests` in `object/keyed_entries.rs`, each run in both collection modes: `keys_compare_by_same_value_zero` (`-0` and `+0`, NaN of two bit patterns, two Strings made apart with the same code units, two objects); `insertion_order_survives_deletes_and_overwrites`; `a_cursor_visits_an_entry_added_before_it_and_skips_one_deleted_before_it`; `compaction_moves_every_cursor_to_the_same_next_entry` (1,000 entries, every second deleted, two cursors at different positions, compaction forced: each cursor's next entry is the same before and after);
