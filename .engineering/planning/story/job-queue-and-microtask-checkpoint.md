## Context

Slice 10 brings jobs, `Promise`, `async` functions and generators and `for await` (`epic:slice-10-promises-and-async`; `docs/design/engine.md`, section 12, item 10). It is delivered after slice 7 and before slices 4, 9 and 8 (the line `order delivery 1,2,3,6,5,7,10,4,9,8,...` of the `swell-slices` block). Its first consumer, the testharness.js tests of the HTML parser of surf (`docs/plan/waves.md`, "The order after slice 6"), lacks one function of `resources/testharness.js` (lines 5032 to 5039 of the downloaded files of that measurement): `async function fetch_json(resource) { const response = await fetch(resource); return await response.json(); }`, exposed as a global (`expose(fetch_json, 'fetch_json')`) and called by neither script nor any test of the parser, so its result is not used. Both values it awaits are promises of the host (`fetch()` and `Response.json()`): the host makes each with `Cx::new_promise_capability` in a host function, later resolves it by `Agent::call` of its resolve function, and drains the queue with `Agent::perform_microtask_checkpoint` after each such call and after each script. The scripts use nothing else of the slice but `Promise.resolve`, `Promise.reject`, `new Promise`, `then` and `catch` (no static that takes an iterable, no `finally`, no `queueMicrotask` of the engine). The first wave of the slice is this story and `story:async-function-syntax-and-early-errors` beside it, then `story:promise-constructor-then-and-jobs`, then `story:async-functions-and-await`, which holds the test of the consumer's shape; none needs an open story of slice 7.

This story brings the queue of the agent and the checkpoint, with host microtasks as the only entries it can make, and the runner's handling of the flag `async`. On the base (`397ffff`) the agent has no queue: the hooks of a promise job exist with their defaults (`crates/swell/src/host/hooks.rs` lines 205 to 260) and nothing calls them; `Job` (line 32) holds a kind and a realm. The runner runs an `async` case as any other (`crates/test262/src/run.rs`, module documentation lines 11 to 13: "`async` cases are run like any other until slice 10 brings `doneprintHandle.js` and the job queue"; `crates/test262/src/count.rs` line 65; `crates/test262/src/host.rs` lines 82 to 84: jobs "are kept, never performed"), so every such case fails on what it reaches first.

Design it follows, by name: `docs/design/host-interface.md` section 11, "Jobs and the microtask checkpoint" (lines 952 to 1057: one FIFO queue in the agent for promise jobs and host microtasks, one step budget for the whole checkpoint, the nested checkpoint that returns at once, ClearKeptObjects after the queue is empty, `CheckpointReport`, `Microtask<H>`, `Agent::queue_microtask`, `Agent::perform_microtask_checkpoint`, `Cx::queue_microtask`, `Cx::perform_microtask_checkpoint`), section 10 (a termination of a checkpoint: the job that was running is dequeued and not run again, the jobs after it stay queued), the reads (`pending_microtasks`, line 1215), HOST-77, HOST-79, HOST-81 and HOST-149; `docs/design/engine.md` decision 4, "Collector" (the job queue is a root, line 1010), and decision 11, the bullet "`async`" (line 1763). ## What later stories reuse

The queue and the loop of the checkpoint: one outermost entry, one step per entry dequeued, the order of one FIFO for every kind of entry, the flag of a running checkpoint, what a termination leaves, the counts of `CheckpointReport` and `pending_microtasks`. `story:promise-constructor-then-and-jobs` adds the entry of a promise job (its record, its root, its charge, the hooks around it) to the same queue and loop, and cases with `then` to the runner's fixture tree of this story; `story:async-functions-and-await` resumes an activation from a promise job of that loop.

## Domain relations

- Agent → microtask queue entries: one to many, owned; an entry lives from its enqueue until the checkpoint that dequeues it, across entries, and is dropped with the agent — declared for jobs (`spec/domains/host.yaml:165`, the relation `jobs` of the agent, `owns`, many, and the lifecycle `Enqueued` → `Ran` of `swell.host.Job` at `:366`); inferable for host microtasks, which the model does not hold (inferred from `docs/design/host-interface.md:954`, one queue for both kinds, and `crates/swell/src/host/agent.rs:143`, the `Agent`). The model has no state for an entry a termination dequeued without running it (section 10: "not run again"); this story does not change `spec/` and names the gap in its report.

- Host microtask → realm: many to one; the realm given when it was queued is its current realm while it runs — inferable (inferred from `docs/design/host-interface.md:711`, the realm of each entry point, and the design change named in Context; no ess/1 document declares a host microtask).

- Running checkpoint → its entries: one to many; the checkpoint is one outermost entry and every entry it runs spends from its one step budget — inferable (inferred from `docs/design/host-interface.md:955` and `spec/domains/host.yaml:50`, the comment "a microtask checkpoint is one entry", which the model marks UNMAPPED).

- `Cx::perform_microtask_checkpoint(&mut self) -> Completion<CheckpointReport>`: while `checkpointing` is set it answers `Ok` with both counts 0 at once and runs nothing (HOST-81; `html:perform-a-microtask-checkpoint`, "If the event loop's performing a microtask checkpoint is true, then return"); otherwise (a host function that a script called) it runs the same loop inside the running entry, on that entry's step budget, a termination being that entry's, with `checkpointing` set for its duration; a microtask it runs that calls into code re-enters above the caller's frames, counted against `reentry_depth` as every call from a host function is.

- Bounds, as the design states them and the design changes of the wave fix them. Steps: one step per entry dequeued, beside the steps its code spends; a checkpoint with nothing queued spends none. Memory: a host microtask is a Rust closure of the host and is not charged to the agent (`docs/design/engine.md` decision 4 charges what the engine allocates for script; the promise job of the next story is charged); dropping the agent drops every queued closure. Termination: `StepBudget`, `MemoryBudget` and `Interrupted` alike end the checkpoint after the entry that was running, which is not run again; `EngineFault` faults the agent and the queue is never run.
